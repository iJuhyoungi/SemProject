# HAB 와 OTP — 하드웨어 Root of Trust 설계

이 문서는 **소프트웨어만으로는 닫을 수 없는 위협**을, 하드웨어를 도입하면 어떻게 닫는지
설계 수준으로 정리한 것입니다.

**이 프로젝트에서 퓨즈는 굽지 않습니다.** eFuse 는 비가역이라 학습용 보드 한 대 환경에서
실패하면 영구 브릭입니다. 그래서 "어떻게 하는가" 를 문서로 남기고, 실제 굽기는
[Threat Model](THREAT_MODEL.md) 의 범위에서 의도적으로 제외했습니다.

## 무엇이 남아 있는가

하드닝(H-1 ~ H-3)을 마친 뒤에도 닫히지 않은 위협입니다.

| 위협 | 내용 | 왜 SW 로 못 닫는가 | 필요한 하드웨어 |
|---|---|---|---|
| **T-08** | Stage 1 을 검증 없는 버전으로 교체 | Stage 1 도 재기록 가능한 flash 위에 있고, ROM 이 이를 검증하지 않음 | HAB + eFuse SRK |
| **T-09** | Stage 1 에 박힌 root 공개키를 공격자 키로 교체 | T-08 과 같은 뿌리 | HAB + eFuse SRK |
| **T-05** | 옛 정책(서명 진짜)을 되돌려 폐기·anti-rollback 무력화 | 카운터가 flash 에 있으면 되돌릴 수 있음. 보장 장치를 또 다른 SW 에 두면 무한 회귀 | OTP monotonic counter |
| **T-17** | SWD/JTAG 로 부팅 흐름 직접 조작 | 디버그 포트는 SW 계층 밖에서 메모리를 건드림 | eFuse DAP disable |

공통점이 하나 있습니다. **되돌릴 수 없음(irreversibility)을 소프트웨어가 만들어낼 수 없다는
것**입니다. 퓨즈는 물리적으로 0→1 단방향이라 그 성질을 하드웨어가 제공합니다.

# 1부 · HAB — Stage 1 의 진정한 불변성

## HAB 가 하는 일

i.MX RT1020 의 Boot ROM 에는 **HAB (High Assurance Boot, HABv4)** 가 들어 있습니다. ROM 은
마스크 ROM 이라 제조 시점에 고정되며 재기록이 불가능합니다. 즉 **ROM 자체가 신뢰 기점**입니다.

HAB 를 켜면 ROM 이 부팅 이미지를 실행하기 전에 서명을 검증합니다. 검증에 쓰는 공개키의
신뢰는 **eFuse 에 구운 해시**에서 나옵니다.

```
┌─────────────────────────────────────────────────────────┐
│ eFuse (OCOTP) — 비가역                                   │
│   SRK_HASH = SHA-256( SRK table )                        │
│   SEC_CONFIG = Closed                                    │
└──────────────────────┬──────────────────────────────────┘
                       │ ROM 이 부팅 때마다 대조
┌──────────────────────▼──────────────────────────────────┐
│ Boot ROM (mask ROM, 변경 불가)                            │
│   1. IVT 를 읽어 CSF 위치를 찾음                           │
│   2. CSF 안의 SRK table 해시를 퓨즈 값과 대조               │
│   3. SRK 로 CSF 서명 검증 → 이미지 서명 검증                │
│   4. 실패하면 실행하지 않음                                │
└──────────────────────┬──────────────────────────────────┘
                       ▼
                   Stage 1 (이제 진짜로 불변)
```

## 구성 요소

| 이름 | 역할 |
|---|---|
| **SRK** (Super Root Key) | HAB 의 최상위 키. RSA 키쌍 **최대 4개**를 SRK table 에 담습니다 |
| **SRK table hash** | SRK table 의 SHA-256. **이 해시만 퓨즈에 굽습니다** (키 자체가 아님) |
| **CSF** (Command Sequence File) | ROM 에게 "무엇을 어떻게 검증하라" 를 지시하는 명령 블록. 이미지에 덧붙습니다 |
| **CST** (Code Signing Tool) | NXP 가 배포하는 호스트 도구. CSF 를 만들고 서명합니다 |
| **IVT** | 이미지 진입점·CSF 위치 등을 담은 벡터. 이 프로젝트도 이미 쓰고 있습니다 (`0x60000000` 영역) |
| **SEC_CONFIG** | Open / Closed 를 정하는 퓨즈. **Closed 여야 검증 실패 시 실행이 차단**됩니다 |

## 왜 키가 아니라 해시를 굽는가

퓨즈 공간은 매우 좁습니다 (수십~수백 비트 수준). RSA-2048 공개키 4개를 통째로 넣을 수
없습니다. 대신 **SRK table 의 SHA-256 해시 32바이트만** 굽고, 실제 키는 CSF 에 담아 이미지와
함께 flash 에 둡니다.

공격자가 SRK table 을 자기 키로 바꾸면 해시가 달라져 퓨즈 값과 불일치하므로 ROM 이 거부합니다.
**우리가 H-3b 에서 만든 키 인증서와 정확히 같은 발상**입니다 — 큰 것은 데이터로 두고, 작고
바꿀 수 없는 곳에는 그 지문만 둡니다.

## Open 과 Closed

| SEC_CONFIG | 동작 |
|---|---|
| **Open** (기본) | HAB 가 검증은 수행하고 **이벤트를 기록하지만, 실패해도 부팅은 계속**합니다 |
| **Closed** | 검증 실패 시 **실행하지 않습니다** |

여기가 이 프로젝트의 결정적인 갈림길입니다. **Open 상태에서는 서명 파이프라인 전체를 안전하게
연습할 수 있습니다.** 이미지를 CST 로 서명해 굽고, 부팅한 뒤 HAB 이벤트를 읽어 "검증이
통과했는가" 를 확인할 수 있습니다. 브릭 위험이 없습니다.

**Closed 로 굽는 순간부터 되돌릴 수 없습니다.** 서명이 잘못된 이미지를 굽는 순간 그 보드는
더 이상 부팅하지 않습니다. 그래서 실무에서는 Open 상태에서 이벤트 로그가 완전히 깨끗해질
때까지 반복 검증한 뒤에야 Closed 로 넘어갑니다.

> 이 프로젝트가 멈춘 지점이 정확히 여기입니다. Open 에서의 연습까지는 브릭 위험이 없지만,
> 보드가 한 대뿐이라 Closed 이후의 실수를 감당할 수 없습니다.

## 도입 절차 (설계)

```
1. SRK 키쌍 4개 생성 (CST 의 hab4_pki_tree 스크립트)
2. SRK table 생성 → SRK table hash 산출 (srktool)
3. CSF 작성 — 서명 대상 영역(Stage 1 + IVT + boot data) 지정
4. CST 로 이미지 서명 → CSF 를 이미지에 덧붙임
5. 서명된 이미지를 flash 에 굽고 부팅
6. HAB 이벤트 확인 (ROM API 또는 디버거로 hab_status 조회)
   → 이벤트가 없어야 함. 있으면 CSF/영역 지정을 고칠 것
7. (여기까지 브릭 위험 없음)
--------------------------------------------------------
8. SRK_HASH 퓨즈 굽기         ← 비가역
9. 다시 부팅해 이벤트 재확인
10. SEC_CONFIG = Closed 굽기  ← 비가역, 실수 시 영구 브릭
```

각 단계의 정확한 퓨즈 주소·비트 폭·CST 명령은 칩과 툴 버전에 따라 다릅니다. **확인처**입니다.

- RM 의 **System Boot** 장 (IVT/boot data 구조), **OCOTP** 장 (퓨즈 맵)
- NXP **AN4581** (HABv4 secure boot 적용 노트)
- CST 배포판의 사용자 가이드

## 무엇이 닫히는가

**T-08 / T-09 가 닫힙니다.** Stage 1 과 거기 임베드된 root 공개키가 ROM 검증을 통과해야만
실행되므로, 공격자가 Stage 1 을 바꾸면 부팅 자체가 되지 않습니다. 지금까지 "관례"였던 Stage 1
의 불변성이 **강제**가 됩니다.

[Architecture](ARCHITECTURE.md) 의 신뢰 경계 A(ROM → Stage 1)가 여기서 닫힙니다.

## SRK 폐기 — root 키 유출 대응

[Key Management](KEY_MANAGEMENT.md) 에서 "root 키가 유출되면 복구할 수 없다" 를 가장 약한
고리로 남겨뒀습니다. HAB 는 이걸 완화합니다.

SRK 슬롯이 4개이고 **SRK_REVOKE 퓨즈로 개별 폐기**가 가능합니다. 1번 키가 유출되면 그
슬롯을 폐기하고 2번 키로 서명한 이미지를 배포합니다. 슬롯 수만큼(최대 3회) 여유가 있습니다.

이것도 퓨즈라 **비가역**입니다. 폐기는 되돌릴 수 없고 슬롯은 소진됩니다. 우리가 H-3c 에서
만든 `min_key_version` 과 같은 원리이며, 차이는 **되돌릴 수 없다는 보장이 하드웨어에서
온다**는 점입니다.

# 2부 · OTP Monotonic Counter — 정책 rollback 차단

## 문제 재확인 (T-05)

메타데이터의 `seq`, `min_acceptable_version`, `min_key_version` 은 전부 flash 에 있습니다.
공격자가 옛 정책(서명 진짜)을 되돌리면 anti-rollback 과 키 폐기가 함께 무력화됩니다.

RSA 서명으로는 막을 수 없습니다. **옛 정책도 우리가 진짜로 서명한 것**이기 때문입니다.
서명은 "누가 만들었나" 를 증명하지 "언제 것인가" 를 증명하지 않습니다.

## 왜 SW 로 불가능한가

"최신 seq 를 어딘가에 기록해두고 대조하면 되지 않나" 는 발상은 무한 회귀에 빠집니다.

```
정책 seq 를 flash A 에 기록 → A 를 되돌리면 무력화
A 의 무결성을 flash B 로 보호 → B 를 되돌리면 무력화
B 를 flash C 로 보호 → ...
```

되돌릴 수 없는 저장소가 사슬 어딘가에 **반드시 하나는** 있어야 끊깁니다.

## 퓨즈 카운터의 설계

퓨즈는 **0→1 단방향**입니다. 이 성질을 그대로 카운터로 씁니다.

### 단항(unary / thermometer) 인코딩

일반적인 이진 카운터는 쓸 수 없습니다. 2진수로 세면 `0111 → 1000` 처럼 **1을 0으로
되돌려야 하는 순간**이 오는데, 퓨즈는 그걸 못 합니다.

대신 비트를 하나씩 태웁니다.

```
세대 0 : 0000 0000 0000 0000
세대 1 : 0000 0000 0000 0001
세대 2 : 0000 0000 0000 0011
세대 3 : 0000 0000 0000 0111
...
카운터 값 = popcount(fuse word)
```

읽기는 `popcount`, 증가는 다음 비트 하나 태우기. 항상 단조 증가하고 되돌릴 수 없습니다.

### 예산 계산

**비트 하나가 세대 하나**이므로 예산이 유한합니다. 32비트 퓨즈 워드 하나면 **32세대**입니다.

| 용도 | 예상 빈도 | 32비트로 |
|---|---|---|
| 보안 패치 세대 | 연 1~2회 | 16~32년 |
| 키 폐기 세대 | 유출 시에만 | 충분 |
| 일반 릴리스 | 월 1회 | **3년 미만 — 부족** |

**핵심 설계 판단**: OTP 카운터는 **모든 릴리스마다 올리는 게 아니라, 되돌리면 안 되는
보안 사건에만 올립니다.** 일반 버전 관리는 지금처럼 flash 정책(`min_acceptable_version`)이
담당하고, OTP 는 그 정책의 세대를 봉인하는 역할만 합니다.

### 정책과의 결합

```
metadata (flash, root 서명)
  ├─ seq
  ├─ min_acceptable_version
  ├─ min_key_version
  └─ policy_generation        <- 신규. OTP 카운터와 대조할 값

부팅 시 Stage 2 의 검사:
  otp_gen = popcount(OCOTP_GP_word)
  if (metadata.policy_generation < otp_gen)  → 거부 (옛 정책 rollback)
  if (metadata.policy_generation > otp_gen)  → 퓨즈를 태워 따라잡음 (commit)
```

옛 정책을 되돌리면 `policy_generation` 이 OTP 값보다 작아져 거부됩니다. 퓨즈는 되돌릴 수
없으니 공격자가 OTP 를 낮출 방법이 없습니다. **T-05 가 닫힙니다.**

### 퓨즈를 태우는 시점 — 가장 위험한 결정

"새 정책을 보면 바로 태운다" 는 위험합니다. 새 정책의 App 이 실제로 부팅되는지 확인하기
전에 옛 정책으로 돌아갈 길을 스스로 끊는 것이기 때문입니다.

실무 순서는 이렇습니다.

```
1. 새 정책 + 새 App 을 굽는다 (퓨즈는 아직 안 태움)
2. 부팅해서 App 이 정상 동작하는지 확인
3. App 이 "정상 기동" 을 보고한다 (watchdog 해제, 헬스체크 통과 등)
4. 그 다음 부팅에서 비로소 퓨즈를 태워 세대를 확정 (commit)
```

이 패턴은 A/B 업데이트의 **commit / rollback 창(window)** 과 같은 구조입니다. 이 프로젝트는
이미 A/B 와 fallback 을 갖추고 있으니, 그 위에 "확정" 단계를 얹는 형태가 됩니다.

### 전원 끊김 안전성

퓨즈 굽기 도중 전원이 끊기면 비트가 어중간하게 프로그램될 수 있습니다. 완화책입니다.

- **한 번에 한 비트만** 태웁니다. 단항 인코딩이 여기에 유리합니다.
- 태운 직후 **다시 읽어 확인**하고, 실패면 같은 비트를 재시도합니다 (같은 비트를 다시
  태우는 것은 안전합니다 — 이미 1인 비트를 1로 만드는 연산이므로).
- `popcount` 기반이라 비트 순서가 어긋나도 값이 흔들리지 않습니다.

### 확인처

OCOTP 의 general purpose 퓨즈 워드 위치·개수, 프로그래밍 타이밍(전압·펄스 폭), shadow
register 갱신 절차는 칩마다 다릅니다.

- RM 의 **OCOTP** 장 — 퓨즈 맵, GP 워드, 프로그래밍 시퀀스
- ROM API 의 퓨즈 프로그래밍 인터페이스 (있는 경우) 또는 OCOTP 레지스터 직접 제어

## 대안 저장소

퓨즈 예산이 부족하거나 더 유연한 카운터가 필요할 때의 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **eFuse OTP** | 추가 부품 없음, ROM 과 같은 신뢰 수준 | 예산이 유한(수십 세대), 비가역 |
| **TPM / Secure Element** | 카운터 개수·범위가 넉넉, 키 보관도 겸함 | 부품·BOM 증가, 버스 통신 보호 필요 |
| **RPMB** (eMMC/UFS) | 대용량, 모바일 표준 | eMMC 필요. 이 보드는 NOR flash 라 해당 없음 |
| **TrustZone secure storage** | SW 로 격리 | Cortex-M33/M85 급 필요. M7 에는 없음 |

이 보드(RT1020, Cortex-M7, NOR flash)에서 현실적인 선택은 **eFuse OTP** 하나입니다.

# 3부 · 디버그 포트 (T-17)

SWD/JTAG 가 열려 있으면 지금까지의 모든 방어를 옆에서 관통할 수 있습니다. 공격자가 메모리를
직접 읽고 쓰고, PC 를 조작해 검증을 건너뛸 수 있습니다.

퓨즈로 DAP(Debug Access Port)를 잠그면 막힙니다. 다만 트레이드오프가 큽니다.

- **잠그면 현장 디버깅이 불가능**해집니다. 반품된 불량품 분석도 못 합니다.
- 일부 칩은 **인증 기반 디버그 재개방**을 지원합니다 (챌린지-리스폰스로 임시 해제).
- 개발용 보드와 양산 보드의 퓨즈 설정을 분리해야 합니다.

이 프로젝트에서는 pyOCD 로 플래시하고 있어 **잠그면 작업 자체가 불가능**합니다. 명시적으로
범위 밖입니다.

# 결합 후의 전체 그림

HAB 와 OTP 를 도입했을 때의 신뢰 사슬입니다. 굵은 부분이 하드웨어가 담당하는 영역입니다.

```
┌──────────────────────────────────────────────────────────┐
│ ** eFuse: SRK_HASH / SEC_CONFIG=Closed / SRK_REVOKE **   │  비가역
│ ** eFuse: policy_generation counter (OTP) **             │
└────────────────────┬─────────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────────┐
│ ** Boot ROM (mask ROM) — HAB 검증 **                      │  변경 불가
└────────────────────┬─────────────────────────────────────┘
                     │ CSF 서명 검증 통과해야 실행
┌────────────────────▼─────────────────────────────────────┐
│ Stage 1 — 이제 진짜로 불변 (T-08, T-09 닫힘)               │
│   root 공개키 임베드                                       │
└────────────────────┬─────────────────────────────────────┘
                     │ RSA-2048 + fault injection 하드닝
┌────────────────────▼─────────────────────────────────────┐
│ Stage 2 — 검증자 + 정책 판단                               │
│   정책 generation 을 OTP 카운터와 대조 (T-05 닫힘)          │
│   키 인증서 검증 + 폐기 (T-16 닫힘)                         │
└────────────────────┬─────────────────────────────────────┘
                     │ release 키 + measured boot
┌────────────────────▼─────────────────────────────────────┐
│ App A / App B                                             │
└──────────────────────────────────────────────────────────┘
```

**소프트웨어 사슬이 위쪽 두 계층만 하드웨어로 교체하면 그대로 완성된다**는 점이 중요합니다.
Stage 2 이하의 구조는 바꿀 필요가 없습니다. 지금까지 만든 것이 버려지지 않습니다.

# 퓨즈 없이 확인할 수 있는 것

브릭 위험 없이 여기까지는 실제로 해볼 수 있습니다.

| 항목 | 방법 | 위험 |
|---|---|---|
| CST 로 CSF 생성·이미지 서명 | 호스트에서만 수행 | 없음 |
| HAB Open 상태에서 서명 이미지 부팅 | 평소처럼 flash | 없음 |
| HAB 이벤트 로그 확인 | ROM API `hab_status` 또는 디버거로 이벤트 영역 조회 | 없음 |
| 서명 깨진 이미지의 HAB 이벤트 확인 | 일부러 변조해 부팅 | 없음 (Open 이라 부팅은 계속됨) |
| OTP 카운터 **읽기** 로직 | shadow register 읽기만 | 없음 |
| OTP 카운터 **쓰기** 로직 | — | **비가역. 하지 않음** |

즉 **"굽기 직전까지" 는 전부 검증 가능**합니다. 실제 제품 과제를 수주하면 이 순서로 진행하고,
Closed 전환은 개발용 보드를 별도로 확보한 뒤에 합니다.

# 요약

| 위협 | SW 사슬 | 하드웨어 도입 후 |
|---|---|---|
| T-08 Stage 1 교체 | 열림 | **닫힘** — HAB + SRK_HASH 퓨즈 |
| T-09 공개키 교체 | 열림 | **닫힘** — 같은 메커니즘 |
| T-05 정책 rollback | 열림 | **닫힘** — OTP monotonic counter |
| T-17 디버그 포트 | 열림 | **닫힘** — DAP disable 퓨즈 (트레이드오프 큼) |
| root 키 유출 | 복구 불가 | **완화** — SRK 슬롯 4개 + SRK_REVOKE |

실무 수준의 secure boot 은 **소프트웨어 사슬과 hardware root of trust 의 결합**으로
완성됩니다. 이 프로젝트는 소프트웨어 쪽을 끝까지 밀어붙였고, 그 경계가 어디이며 하드웨어가
무엇을 담당하는지를 정확히 아는 것이 결론입니다.
