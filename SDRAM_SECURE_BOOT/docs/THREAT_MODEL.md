# Threat Model

이 프로젝트의 secure boot 이 **무엇을 누구로부터 지키는지**, 그리고 **무엇을 지키지
않기로 했는지**를 정리한 문서입니다. 하드닝 작업 (H-1 이후) 은 모두 이 문서의 위협
목록에서 출발합니다.

## 왜 위협모델을 먼저 쓰는가

하드닝은 방어를 계속 덧붙이는 일이 되기 쉽습니다. 그러면 "왜 이 방어를 넣었는가" 에
답할 수 없고, 반대로 "이건 왜 안 넣었는가" 도 설명하지 못합니다. 위협모델은 하드닝의
채점 기준표입니다. 공격자에게 무엇을 허용했는지, 어떤 자산을 지키는지, 무엇을 의도적으로
포기했는지를 먼저 고정해 두면 이후 작업은 이 표의 빈칸을 채우는 일이 됩니다.

또 하나 중요한 점이 있습니다. 위협모델이 없으면 **범위 밖의 위협을 "구현 실패" 처럼
보이게 만듭니다**. 이 프로젝트는 eFuse 를 굽지 않기로 이미 결정했는데, 그 결정을 문서로
남기지 않으면 hardware root of trust 부재가 그냥 결함으로 읽힙니다. 의도적 제외와 미처
못 막은 구멍은 구분되어야 합니다.

## 1. 보호 자산

| ID | 자산 | 지키고자 하는 속성 | 훼손 시 결과 |
|---|---|---|---|
| **AS-1** | Stage 1 코드와 여기 임베드된 공개키 modulus | 무결성 (변경 불가) | 사슬의 뿌리가 무너집니다. 이후 모든 검증이 무의미해집니다. |
| **AS-2** | Stage 2 / App A / App B 이미지 | 진정성 (authenticity) | 공격자 코드가 특권 상태로 실행됩니다. |
| **AS-3** | 메타데이터 (`seq`, `min_acceptable_version`) | 무결성 + **monotonic 성** | 취약점이 있던 옛 버전으로 되돌릴 수 있습니다. |
| **AS-4** | 이미지 서명용 private key | 기밀성 | 공격자가 임의 코드에 유효한 서명을 붙일 수 있습니다. 사슬 전체가 무력화됩니다. |
| **AS-5** | 부팅 시의 실행 제어 흐름 (점프 판정) | 무결성 | 검증을 통과하지 않은 이미지로 점프합니다. 서명 검증 자체를 우회합니다. |
| **AS-6** | 부팅 가용성 (보드가 벽돌이 되지 않을 것) | 가용성 | 필드에서 복구 불가능해집니다. A/B 와 이중 메타데이터가 이걸 위한 장치입니다. |

AS-4 는 **보드 위에 존재하지 않습니다**. private key 는 호스트 PC 에만 있고 보드에는
public modulus 만 임베드됩니다. 따라서 보드를 물리적으로 확보한 공격자가 부채널로 키를
빼내는 시나리오는 이 프로젝트에 성립하지 않습니다.

## 2. 신뢰 경계

```
            ┌──────────────────────────────────────────────┐
   호스트    │  서명 파이프라인 (private key 보관)            │  ← 경계 D
   (신뢰)    │  build.sh / patch_stage2_header.py           │
            └───────────────────┬──────────────────────────┘
                                │ 서명된 이미지·메타데이터 (bin)
       ─────────────────────────┼──────────────────────────────── 경계 D
                                ▼
            ┌──────────────────────────────────────────────┐
            │  NXP Boot ROM (mask ROM, 변경 불가)            │
            └───────────────────┬──────────────────────────┘
                                │  ← 경계 A : 검증 없음 (하드웨어 갭)
            ┌───────────────────▼──────────────────────────┐
            │  Stage 1  — verifier 1                        │  신뢰 기점 (가정)
            └───────────────────┬──────────────────────────┘
                                │  ← 경계 B : RSA-2048 검증
            ┌───────────────────▼──────────────────────────┐
            │  Stage 2  — verifier 2 + 정책 판단             │
            └───────────────────┬──────────────────────────┘
                                │  ← 경계 C : RSA-2048 검증 + anti-rollback
            ┌───────────────────▼──────────────────────────┐
            │  App A / App B  — 최종 페이로드                 │
            └──────────────────────────────────────────────┘

   ※ SWD / JTAG 디버그 포트는 위 모든 계층을 옆에서 관통합니다  ← 경계 E
```

| 경계 | 통과 조건 | 현재 상태 |
|---|---|---|
| **A** — ROM → Stage 1 | (없음) | **열려 있습니다.** ROM 은 Stage 1 을 검증하지 않습니다. HAB / eFuse SRK 영역입니다. |
| **B** — Stage 1 → Stage 2 | vector sanity → magic → size → CRC32 → SHA-256 → RSA-2048 | 닫혀 있습니다 (`shared/src/verify.c`). |
| **C** — Stage 2 → App | 경계 B 와 동일한 검증 + `version >= min_acceptable_version` | 닫혀 있습니다. 단 정책 자체의 monotonic 성은 보장되지 않습니다 (T-05). |
| **D** — 호스트 → 보드 | private key 보유 여부 | 키 관리 체계가 없습니다 (T-16). |
| **E** — 디버그 포트 | (없음) | 열려 있습니다. eFuse 로 DAP 를 잠그는 영역이라 범위 밖입니다. |

**신뢰 기점 (root of trust) 의 정의**: 이 프로젝트는 *"Stage 1 과 거기 임베드된 공개키는
변조되지 않았다"* 를 **가정**하고 그 위에 사슬을 세웁니다. 이건 증명이 아니라 가정이며,
가정을 사실로 만들려면 경계 A 에 하드웨어가 들어와야 합니다.

## 3. 공격자 모델

각 위협은 아래 공격자 등급 중 하나를 전제로 합니다. 등급이 높을수록 필요한 장비와
접근 수준이 올라갑니다.

| ID | 공격자 | 가정하는 능력 | 필요한 접근 |
|---|---|---|---|
| **AT-1** | 논리 공격자 | 이미지 슬롯과 메타데이터 sector 에 **임의의 내용을 flash 할 수 있습니다**. 앱의 OTA 경로를 장악했거나 부팅 후 앱 취약점으로 flash 쓰기 권한을 얻은 상황입니다. private key 는 없습니다. | 원격 또는 논리적 |
| **AT-2** | 물리 접근 공격자 | AT-1 에 더해 보드를 손에 쥐고 SWD 로 임의 메모리를 읽고 쓸 수 있습니다. flash 칩을 직접 다룰 수 있습니다. | 물리적 |
| **AT-3** | Fault injection 공격자 | AT-2 에 더해 전압 / 클럭 / EM 글리치로 **명령 실행 하나를 건너뛰거나 레지스터 값 하나를 망가뜨릴 수 있습니다**. 한 부팅에 성공적인 글리치 1회를 가정합니다 (다회는 난이도가 급격히 올라갑니다). | 물리적 + 장비 |
| **AT-4** | 공급망 / 내부자 | 빌드 서버나 개발자 PC 를 통해 private key 에 접근하거나, 서명 파이프라인에 개입합니다. | 조직 내부 |

**핵심 가정**: **AT-1 을 기본선으로 둡니다.** "flash 는 언제든 다시 쓰일 수 있다" 를
전제로 설계합니다. 이 가정이 이 프로젝트에서 제일 중요합니다. 여기서 anti-rollback 의
근본 한계 (T-05) 와 Stage 1 불변성의 한계 (T-08) 가 모두 파생됩니다.

**AT-3 이 하드닝의 주 표적입니다.** 크립토 자체는 이미 견고합니다 (PKCS#1 v1.5 패딩을
전체 검사하고 DigestInfo OID 까지 확인합니다). 그래서 남은 현실적 공격로는 크립토를 깨는
게 아니라 **크립토의 결론을 실어 나르는 제어 흐름을 건드리는 쪽**입니다.

## 4. 범위

### 범위 안 (하드닝 대상)

- 검증 결과가 실행 결정으로 이어지는 **제어 흐름의 견고성** (fault injection 내성)
- **정책과 이미지의 바인딩** (measured boot)
- **키 계층과 폐기** 체계 (설계 + 호스트 툴링)
- 위 셋에 대한 **보드 위 실증** (공격 시연과 방어 전후 비교)

### 범위 밖 — 그리고 그 이유

| 제외 항목 | 이유 |
|---|---|
| **eFuse 굽기** (HAB closed, SRK hash, DAP disable) | **비가역**입니다. 학습용 보드 한 대 환경에서 실패하면 영구 브릭입니다. **H-4 에서 설계 문서로만 다룹니다.** |
| **부채널 키 추출** (전력 / 타이밍 분석) | 보드에 private key 가 없습니다 (AS-4). 검증 연산은 공개키만 씁니다. 지킬 비밀이 없습니다. |
| **OTA 전송 채널 보안** (TLS, 서버 인증) | 이 프로젝트의 신뢰 모델은 "저장된 이미지를 믿지 않는다" 입니다. 전송 경로는 애초에 신뢰하지 않으므로 채널 보안 유무가 결론을 바꾸지 않습니다. |
| **앱 실행 이후의 런타임 공격** (메모리 손상, 권한 상승) | Secure boot 의 책임은 "믿을 수 있는 코드로 시작하는 것" 까지입니다. 그 이후는 runtime attestation / MPU 격리의 영역입니다. |
| **Flash 칩 탈거·교체 (chip-off)** | 소프트웨어로 대응할 수 없습니다. 봉인 / mesh 등 물리 대책 영역입니다. |
| **다중 글리치 (한 부팅에 2회 이상)** | 방어 비용 대비 공격 난이도가 비대칭적으로 높습니다. 단일 글리치 내성을 먼저 확보하는 것이 실무 관례입니다. |

## 5. 위협 목록

상태 표기입니다. **차단** = 현재 코드로 막힙니다 / **부분** = 조건부로 막힙니다 /
**열림** = 현재 막지 못합니다.

### 5.1 이미지 위조 계열

| ID | 위협 | 공격자 | 현재 대응 | 상태 |
|---|---|---|---|---|
| **T-01** | Stage 2 이미지를 공격자 코드로 교체 | AT-1 | Stage 1 의 RSA-2048 서명 검증 (`verify.c:73`) | **차단** |
| **T-02** | App A/B 이미지를 공격자 코드로 교체 | AT-1 | Stage 2 의 동일 검증 | **차단** |
| **T-03** | 이미지 일부 비트 손상 (전송 오류, bit rot) | — | vector sanity + magic + size + CRC32 + SHA-256 | **차단** (가용성은 A/B fallback 이 담당) |
| **T-19** | TOCTOU — 검증한 flash 와 실행하는 flash 가 같은 대상 | AT-2 | 없음. XIP 라 이미지를 RAM 으로 복사하지 않고 flash 에서 직접 검증하고 직접 실행합니다. 검증과 점프 사이에 flash 내용을 바꾸면 이론상 우회됩니다. | **열림** (물리 공격자 + 정밀한 타이밍 필요, 잔여 위험으로 수용) |

### 5.2 Rollback 계열

| ID | 위협 | 공격자 | 현재 대응 | 상태 |
|---|---|---|---|---|
| **T-04** | 옛 버전 앱 재설치 (downgrade) | AT-1 | `version < min_acceptable_version` 이면 거부 (`stage2/main.c:151`) | **부분** — T-05 로 우회됩니다 |
| **T-05** | **메타데이터 rollback** — 옛 정책 (서명은 진짜) 을 두 sector 에 재기록 | AT-1 | 없음. 서명이 진짜라 양쪽 다 검증을 통과하고, 옛 `seq` 가 그대로 채택됩니다. | **열림** — SW 로 닫을 수 없습니다 |
| **T-06** | 메타데이터 내용 위조 (`min_ver` 를 0 으로) | AT-1 | 메타데이터 자체에 RSA-2048 서명 (`metadata.c:18`) | **차단** |
| **T-07** | 메타데이터 두 sector 모두 erase | AT-1 | 둘 다 invalid 면 halt (fail-safe, `stage2/main.c:104`) | **차단** (가용성을 희생하는 선택) |

> **T-05 의 근본 원인**: monotonic 카운터를 소프트웨어가 쓸 수 있는 저장소에 두면, 그
> 저장소를 되돌릴 수 있는 공격자에게는 카운터가 아닙니다. 보장 장치를 또 다른 SW 에 두면
> 그 SW 도 같은 공격에 노출됩니다. 무한 회귀입니다. **eFuse OTP counter / TPM / RPMB
> 같은 되돌릴 수 없는 하드웨어가 사슬에 들어와야 끊깁니다.** H-4 의 설계 대상입니다.

### 5.3 Root of trust 계열

| ID | 위협 | 공격자 | 현재 대응 | 상태 |
|---|---|---|---|---|
| **T-08** | Stage 1 자체를 검증 없는 버전으로 교체 | AT-1 | 없음. Stage 1 도 재기록 가능한 flash 위에 있고, ROM 은 이를 검증하지 않습니다 (경계 A). | **열림** — HAB / eFuse SRK 필요 |
| **T-09** | Stage 1 에 임베드된 공개키 modulus 를 공격자 키로 교체 | AT-1 | 없음. T-08 과 같은 뿌리입니다. 공격자 키를 심으면 공격자 이미지가 정상 검증을 통과합니다. | **열림** — 위와 동일 |
| **T-17** | SWD / JTAG 로 부팅 흐름 직접 조작 | AT-2 | 없음 (경계 E). | **범위 밖** — eFuse DAP disable 영역, H-4 에서 설계로 다룹니다 |

### 5.4 Fault injection 계열 (하드닝 핵심 표적)

| ID | 위협 | 공격자 | 현재 상태 | 대응 |
|---|---|---|---|---|
| **T-10** | **검증 결과 판정 분기를 스킵** — `if (verify_image(...))` 이 단 하나의 분기 명령이라, 그 명령 하나를 건너뛰면 검증 실패한 이미지로 점프합니다 (`stage1/main.c:283`, `stage2/main.c:157`) | AT-3 | **열림** | **H-1** |
| **T-11** | **함수 내부 조기 return 스킵** — `verify_image()` 는 "실패하면 조기 return, 끝까지 도달하면 `return 1`" 구조입니다. 어느 검사의 분기든 하나 스킵되면 그대로 성공 경로로 흘러갑니다. | AT-3 | **열림** | **H-1** |
| **T-12** | **반환값의 hamming distance 가 너무 짧음** — `verify_image()` 는 0/1 (1비트 차이), `metadata_reason_t` 는 `METADATA_OK = 0` 입니다. 글리치로 레지스터가 0 이 되면 그게 곧 "정상" 판정입니다. | AT-3 | **열림** | **H-1** |
| **T-13** | **PS 패딩 루프 무력화** — `rsa.c:39` 의 `0xFF` 검사 루프에서 루프 카운터를 망가뜨리면 패딩 검사가 통째로 건너뛰어집니다. 반복 횟수를 사후 검증하지 않습니다. | AT-3 | **열림** | **H-1** |
| **T-14** | **비상수시간 비교** — hash 비교와 DigestInfo 비교에 `memcmp` 를 씁니다 (`rsa.c:50,59`). 첫 불일치에서 조기 종료하므로 타이밍이 새어 나가고, 조기 종료 지점 자체가 글리치 표적이 됩니다. | AT-3 | **열림** | **H-1** |
| **T-15** | **메타데이터 검증 결과 단일 판정** — `p_ok` / `b_ok` 가 각각 단일 `int` 비교입니다 (`metadata.c:37-38`). 한쪽만 뒤집으면 무효한 메타데이터가 채택됩니다. | AT-3 | **열림** | **H-1** |

> **왜 이 계열이 핵심인가**: 크립토는 이미 제대로 되어 있습니다. RSA-2048 을 수학적으로
> 깨는 것보다 **"서명이 유효하다" 는 결론을 실어 나르는 `if` 문 하나를 건드리는 쪽이
> 압도적으로 쉽습니다.** 실제 상용 부트로더 공격 사례 대부분이 여기에 해당합니다.
> 하드닝의 방향은 "판정을 여러 번, 서로 다른 방식으로, 실패를 기본값으로 두고" 하는
> 것입니다.

### 5.5 정책 바인딩 계열

| ID | 위협 | 공격자 | 현재 상태 | 대응 |
|---|---|---|---|---|
| **T-20** | **Mix-and-match** — 메타데이터 서명은 `magic + seq + min_ver` 만 덮습니다. "이 정책이 어떤 앱을 위한 것인지" 를 말하지 않으므로, 진짜 서명된 옛 앱과 진짜 서명된 다른 세대의 정책을 조합할 수 있습니다. 두 서명이 모두 유효하니 검증은 통과합니다. | AT-1 | **열림** | **H-2** (measured boot — 정책 서명에 앱 SHA-256 측정값 포함) |

### 5.6 키 관리 계열

| ID | 위협 | 공격자 | 현재 상태 | 대응 |
|---|---|---|---|---|
| **T-16** | **단일 키 · 폐기 경로 없음** — 테스트 키 하나를 이미지 서명과 메타데이터 서명에 함께 쓰고, repo 에 커밋되어 있습니다. 키가 유출되면 되돌릴 방법이 전혀 없습니다 (사슬 전체가 즉시 무력화됩니다). | AT-4 | **열림** | **H-3** (root → release 키 계층, 폐기 목록, private key 를 repo 밖 / HSM 가정) |

### 5.7 가용성

| ID | 위협 | 공격자 | 현재 상태 | 판단 |
|---|---|---|---|---|
| **T-18** | Stage 2 를 손상시켜 부팅 불가 상태로 만들기 (DoS) | AT-1 | Stage 1 은 fallback 없이 halt 합니다. | **의도된 선택** — secure boot 에서 가용성보다 무결성이 우선합니다. 검증 실패 시 "일단 부팅" 은 secure boot 의 존재 의의를 부정합니다. App 계층은 A/B fallback 으로 가용성을 확보하지만, verifier 계층은 fail-safe halt 를 택했습니다. |

## 6. 하드닝 목표와 성공 기준

| 작업 | 대응 위협 | 성공 기준 (보드 위에서 확인) |
|---|---|---|
| **H-1** Fault injection 하드닝 | T-10 ~ T-15 | 글리치 모사 하네스로 검증 결과를 강제로 뒤집었을 때, **하드닝 전에는 손상된 이미지가 부팅되고 하드닝 후에는 거부**되는 것을 UART 로 나란히 보입니다. |
| **H-2** Measured boot | T-20 | 진짜 서명된 앱과 진짜 서명된 다른 세대 정책을 조합했을 때 거부되는 것을 보입니다. |
| **H-3** 키 계층 + 폐기 | T-16 | 키가 계층으로 분리되고, 폐기된 키로 서명한 이미지가 거부됩니다. private key 가 repo 에 없습니다. |
| **H-4** HAB/SRK + OTP 설계 문서 | T-05, T-08, T-09, T-17 | 퓨즈를 굽지 않고, "닫으려면 무엇을 어떻게 해야 하는가" 를 설계 수준으로 서술합니다. |

**하드닝 후에도 남는 위험 (잔여 위험)** 입니다.

- **T-05 / T-08 / T-09** — 소프트웨어만으로는 원리적으로 닫을 수 없습니다. 하드웨어
  root of trust 와 OTP monotonic 카운터가 필요합니다. H-4 에서 설계로만 다룹니다.
- **T-17** — eFuse DAP disable 영역이라 범위 밖입니다.
- **T-19** — 물리 공격자와 정밀한 타이밍이 동시에 필요합니다. 이미지를 RAM 으로 복사한
  뒤 검증하고 RAM 에서 실행하면 완화되지만, XIP 구조와 256 KB 이미지 크기를 고려하면
  이 프로젝트에서는 수용하는 쪽이 합리적입니다.
- **다중 글리치** — 단일 글리치 내성까지를 목표로 합니다.

이 잔여 위험들은 **실패가 아니라 명시적 경계**입니다. 소프트웨어 사슬이 어디까지 갈 수
있고 어디서부터 하드웨어가 필요한지를 정확히 아는 것 자체가 이 프로젝트의 결론입니다.

## 7. 이 모델의 가정과 재평가 조건

이 위협모델은 다음 가정 위에 서 있습니다. 가정이 바뀌면 문서를 다시 봐야 합니다.

1. **공격자는 private key 를 갖고 있지 않습니다.** 갖고 있다면 서명 검증 계층 전체가
   무의미해집니다. T-16 이 이 가정을 지키기 위한 작업입니다.
2. **RSA-2048 과 SHA-256 은 계산적으로 안전합니다.** 대규모 양자 컴퓨터가 실용화되면
   RSA 는 무너집니다. 장기적으로는 PQC (ML-DSA 등) 로의 이행이 답이며, 이건 알고리즘
   교체 문제이지 구조 문제가 아닙니다.
3. **한 부팅에 성공하는 글리치는 최대 1회입니다.**
4. **Stage 1 은 변조되지 않았습니다.** 이 프로젝트에서 가장 약한 가정이며, 경계 A 에
   하드웨어가 없기 때문에 생깁니다.

재평가가 필요한 시점입니다.

- 실제 제품에 적용해 eFuse / HAB 를 사용하게 될 때 (가정 4 가 사실이 됩니다)
- OTA 채널이 추가되어 AT-1 의 접근 경로가 넓어질 때
- 서명 알고리즘을 ECDSA 나 PQC 로 교체할 때
